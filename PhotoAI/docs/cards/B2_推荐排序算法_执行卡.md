# B2 推荐排序算法执行卡

## 1. 目标

让首页「推荐」与「最新」不再返回同一顺序：给 `recommend` 一个**时间衰减热度**排序，并保持只含展示作品、分页稳定。

现状（`WorkQueryMapper.xml:48-51`）：

```xml
<choose>
    <when test="tab == 'hot'">ORDER BY (COALESCE(p.likep,0)+COALESCE(p.votecount,0)) DESC,p.pid ASC</when>
    <otherwise>ORDER BY p.cwtime DESC,p.pid ASC</otherwise>
</choose>
```

`recommend` 落到 `otherwise`，因此与 `latest` 完全一致（已实测三 tab 前 5 条，recommend 与 latest 逐条相同）。

依据：`docs/接口冻结_v1.md` §1.3 #5（`recommend` 算法尚未冻结，本次为首次实现）。

## 2. 算法（时间衰减热度）

```
score = (likep*2 + votecount*5 + viewcount/10.0) / SQRT(TIMESTAMPDIFF(HOUR, cwtime, NOW()) + 1)
```

设计意图：

- `likep*2`、`votecount*5`：投票权重高于点赞（投票更稀缺）；
- `viewcount/10.0`：浏览量轻微加权，避免纯刷量；
- 除以 `SQRT(小时数+1)`：新作品有曝光机会，老作品不会永占前排，但衰减比线性更温和；
- `+1` 防止刚发布的作品除以 0。

**不宣称个性化推荐**：这是全局热度衰减，不是按用户行为定制。

## 3. 改法

### 3.0 同时补一个缺失字段（重要）

`WorkQueryMapper.xml` 的 `<sql id="Columns">` 与 `resultMap id="Work"` **都缺少 `p.pcid`**，
导致 `/pwork/list`、`/pwork/{pid}`、`/pwork/mine` 等所有复用它的接口都**不返回 pcid**，
前端编辑页无法预选分类（`work.pcid` 恒为 undefined）。

一并修掉：

1. `Columns` 里 `c.pcname` 前面补 `p.pcid,`：
   ```sql
   COALESCE(p.likep,0) AS likep,u.uname,u.avatar,p.pcid,c.pcname,
   ```
2. `resultMap id="Work"` 里补一行：
   ```xml
   <result column="pcid" property="pcid" javaType="java.lang.String"/>
   ```

该项对既有接口是**纯增量**（多返回一个字段），不得改动任何已有列的顺序语义。

### 3.1 推荐排序

`Backend/src/main/resources/mapper/WorkQueryMapper.xml` 的 `<choose>` 改成三段：

```xml
<choose>
    <!-- 推荐：时间衰减热度，新作品有曝光机会；不是个性化推荐。 -->
    <when test="tab == 'recommend'">
        ORDER BY (COALESCE(p.likep,0)*2 + COALESCE(p.votecount,0)*5 + COALESCE(p.viewcount,0)/10.0)
                 / SQRT(TIMESTAMPDIFF(HOUR, p.cwtime, NOW()) + 1) DESC, p.pid ASC
    </when>
    <when test="tab == 'hot'">ORDER BY (COALESCE(p.likep,0)+COALESCE(p.votecount,0)) DESC,p.pid ASC</when>
    <otherwise>ORDER BY p.cwtime DESC,p.pid ASC</otherwise>
</choose>
```

注意：

- `/10.0` 必须带小数位，避免 MySQL 整数除法丢失精度；
- 保留 `p.pid ASC` 作为稳定分页的次要排序，不得删除；
- `SQRT` 与 `TIMESTAMPDIFF` 均为 MySQL 内置函数，不需要额外索引改造（当前数据量 < 100 行）。
