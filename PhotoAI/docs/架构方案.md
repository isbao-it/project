# PhotoAI Hub 架构方案

## §1 定位与边界

**一句话**：在既有 Spring Boot 单体上，把"只设计了一半"的摄影社区补成**发布→审核→浏览→互动**的完整闭环，并挂一个可量化的 AI 检索作为创新点。

**本期 10 张卡**（顺序见 §11）：基线 → 微信登录 → 发布+EXIF → 审核页 → 评论+点赞 → 分类+收藏+同款 → 关注流 → AI 检索 → Redis → 部署&端到端。

**不做的**：私信（N-05）、订单/礼物（N-02）、NIMA、云端 embedding、图片自动审核（N-04）、支付、Vant、分包。

## §2 架构总览

```
[微信小程序]                     [Spring Boot 2.4.5 / JDK8]            [依赖]
 pages/                         ┌──────────────┐
  首页(画廊) ──GET──────────────> │ Controller   │
  关注流    ──GET──────────────> │  (REST)      │──> MySQL 8 (db_pg)
  详情      ──GET──────────────> │              │      9 表 + 6 视图 + 17 触发器
  发布      ──POST─────────────> │ Interceptor  │──> Redis 7
  我的      ──GET──────────────> │  Auth(白名单)│      限流 / 热门榜
                                 │  Role(角色)  │
                                 │ Service      │──> 推理服务 (FastAPI/ONNX)
                                 │ Mapper       │      CLIP → 512 维向量
                                 └──────────────┘
[后台 layuimini + Thymeleaf] ──> 同一后端 /admin/**
```

**部署形态**：`docker-compose` 四服务 —— mysql / redis / backend / ai（推理服务可选，缺失时搜索降级）。

**关键分层原则**：
- Controller 只做「参数校验 + 权限 → Service」
- **业务规则不写进触发器**（现有 17 个触发器保留，但新逻辑一律进 Java；见 §5.4 双写风险）
- 外部依赖（微信/CLIP/文件）一律走接口注入，便于测试与降级

## §4 接口契约（冻结节 · 卡面只引用不复述）

**统一响应**：`{code:0|数字错误码, msg, data, total?}`；**HTTP 状态与 code 同步**（如 401/403/429）。
**统一鉴权**：`Authorization: Bearer <JWT>`；白名单路径见 §4.7。
**分页**：`page`（1 起）、`size`（默认 10，上限 50）。

## §5 数据库设计

### 5.0 可改范围与迁移原则（用户 2026-10-18 明确：数据库也能改，旧代码也能改）

- **没有"不能动的存量"**：表结构、字段类型、索引、触发器、视图、种子数据、旧 Java 代码，**只要立卡就可以改**。
- 但必须满足三条：① 有**幂等迁移脚本**（`db/migration/V00x__*.sql`，可重复执行）② **改前先 `mysqldump` 备份** ③ 每步可回退。
- **禁止**在业务卡里顺手改 schema / 顺手重构旧类——迁移一律独立成卡（卡 00）。

### 5.1 新增表（DDL 摘要）

```sql
CREATE TABLE favorite (
  fid  VARCHAR(36) NOT NULL PRIMARY KEY,
  uid  VARCHAR(36) NOT NULL,
  pid  VARCHAR(36) NOT NULL,
  ct   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_uid_pid (uid, pid),
  KEY idx_pid (pid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE follow (
  fid        VARCHAR(36) NOT NULL PRIMARY KEY,
  uid        VARCHAR(36) NOT NULL,           -- 关注者
  target_uid VARCHAR(36) NOT NULL,           -- 被关注者
  ct         DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_uid_target (uid, target_uid),
  KEY idx_target (target_uid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE work_exif (
  pid       VARCHAR(36) NOT NULL PRIMARY KEY,
  focal_mm  SMALLINT    NULL,      -- 焦距 mm
  aperture  DECIMAL(3,1) NULL,     -- 光圈 f/8.0 → 8.0
  shutter   VARCHAR(16) NULL,      -- '1/250s'
  iso       SMALLINT    NULL,
  lens      VARCHAR(64) NULL,
  camera    VARCHAR(64) NULL,
  stripped  TINYINT(1)  NOT NULL DEFAULT 1,  -- GPS/序列号已剥离
  KEY idx_query (focal_mm, aperture)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE work_embedding (
  pid        VARCHAR(36) NOT NULL PRIMARY KEY,
  model      VARCHAR(32) NOT NULL DEFAULT 'clip-vit-b16',
  dim        SMALLINT    NOT NULL DEFAULT 512,
  vec        BLOB        NOT NULL,   -- float32 小端，512 维 = 2048 字节
  status     ENUM('pending','ready','failed') NOT NULL DEFAULT 'pending',
  err_msg    VARCHAR(255) NULL,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.2 现有表修改（卡 00 一次性迁移，幂等）

| 表 | 变更 | 迁移注意 |
|---|---|---|
| `user` | `+openid VARCHAR(64) NULL UNIQUE`、`+bio VARCHAR(255)`；`pwd` 改为**可空**（微信用户无密码） | 老数据 openid 为 NULL；`pwd` 置空表示"无密码账号" |
| `pwork` | `wstatus` 枚举 → `('待审核','展示','隐藏','已驳回')`，默认 `待审核`；`+KEY idx_uid_ct (uid,cwtime)`、`+KEY idx_status_ct (wstatus,cwtime)` | 现有 9 条均为 `展示` |
| `liketable` | `+UNIQUE KEY uk_uid_target (uid,targetid,targettype)` | **先清重复**再建索引（保最早一条） |
| **计数字段 → INT** | `pwork.viewcount/votecount/likep`、`comment.likecom`、`pcatogory.pc_count`、`gift.stocknum/need`、`user.vote` 全为 `varchar(36)` → **INT UNSIGNED** | 转换前查非数字值：`WHERE col NOT REGEXP '^[0-9]+$'`；视图里的 `cast(... as unsigned)` 一并删掉 |
| `comment` | `+KEY idx_pid_ct (pid,comct)` | 评论列表分页 |
| `sys_log` | `+KEY idx_ct (createtime)` | 后台日志倒序 |
| **外键**（可选但推荐） | 互动表级联：`liketable/favorite/comment/work_exif/work_embedding` 的 `pid` → `pwork.pid` **ON DELETE CASCADE**；`uid` → `user.uid` **RESTRICT** | 建 FK 前先清孤儿行（`LEFT JOIN ... IS NULL`）；`pwork` 本身**不**被级联删 |
| **种子数据** | 10 个真实手机号用户 → **换演示账号**（`demo01..demo10` + 假号），9 个作品作者映射到 demo 账号 | 顺带解决 §4 的脱敏问题；老用户数据归档为 `legacy` 前缀 |

> **为什么要把 varchar 计数改 INT**：`view_work_hot` 现在靠 `cast(... as unsigned)` 兜底排序，别处（如 `likep+1`）仍按字符串算；改成 INT 后排序/累加/索引都正常，也省掉视图里的 cast。

### 5.4 触发器与视图的处置（**原则：触发器只做技术默认值，不做业务计算**）

| 现状 | 处置 | 理由 |
|---|---|---|
| `tri_*_before_insert`（pwork/user/comment/vote/gift… 生成 UUID） | **保留** | 纯技术默认值，无业务语义，删了要改 12 个 Controller |
| `tri_liketable_after_insert/delete`（维护 `pwork.likep`） | **本卡删除这 2 个**，计数改由 **Java 事务维护** | ① 业务规则藏在 DB 里单测测不到；② 与 Java 双写会双重计数 |
| `tri_vote_after_insert/delete`（维护 `votecount`/`likecom`） | **暂留**（投票接口仍在用触发器）→ 等投票卡把计数搬进 Java 后再删 | 避免本期把还能用的功能改坏 |
| `tri_order_*`（订单状态与时间戳） | **保留**（本期不做订单，不接线） | 未来 N-02 的规格 |
| `view_work_detail` / `view_work_hot` | **保留**，但删除 `cast(... as unsigned)`（计数已改 INT） | 列表/详情/热门榜统一走视图 |
| `view_comment_full` / `view_gift_stat` / `view_order_info` / `view_user_stat` | **保留**（未引用），`view_user_stat` 已去掉 `pwd` | 未来补评论/订单时直接用 |
| `proc_create_order` / 2 个 event | **保留**，注释标明"规格，未接线" | N-02 依据 |

> **迁移顺序（卡 00）**：备份 dump → 清重复点赞 → 建唯一索引 → 计数改 INT（先查脏值）→ 删 4 个计数触发器 → 重建视图（去 cast）→ 加索引/外键 → 换演示种子数据。
> **回退**：迁移脚本每步独立可分；失败用备份 dump 恢复。

## §6 错误码枚举（10 个，不含 0）

| code | HTTP | 含义 | 触发 |
|---:|---:|---|---|
| 0 | 200 | 成功 | — |
| 400 | 400 | `invalid_request` | 参数缺失/格式错/分页越界 |
| 401 | 401 | `unauthenticated` | 无 token / 过期 / 白名单外未登录 |
| 403 | 403 | `forbidden` | 角色不足 / 非作者改删他人资源 |
| 404 | 404 | `not_found` | 作品/用户/评论不存在 |
| 409 | 409 | `conflict` | 状态非法（重复 approve、删有作品的用户、关注自己） |
| 413 | 413 | `payload_too_large` | 图片 >10MB |
| 422 | 422 | `content_rejected` / `invalid_image` / `invalid_profile` | 文本审核拒绝；EXIF 解析失败；昵称超长 |
| 429 | 429 | `too_many_requests` | 登录限流（5 次/60s/IP） |
| 500 | 500 | `internal_error` | 未捕获异常（**不吐堆栈给前端**） |
| 503 | 503 | `service_unavailable` | 微信接口不可用（且未开 Mock）/ AI 服务不可用（搜索已降级时**不返回** 503，只在 `/health` 体现） |

> 口径：**HTTP 状态码承载语义**，`body.code` 与之相同；业务拒绝（内容违规）用 **422**，不用 200。

## §8 关键流程时序（5 条）

**① 微信登录（首登建号）**
```
小程序 wx.login() → code
  → POST /auth/wxlogin {code}
  → WeChatClient.code2Session(code)  ──失败──> 若开 Mock：用 dev:{code} 作 openid；否则 503
  → SELECT user WHERE openid = ?
      命中 → 签发 JWT
      未命中 → INSERT user(openid, uname='摄影师xxxx', role='普通用户', status='正常') → 签发 JWT
  → 返回 {token, uid, isNew}
```

**② 游客浏览**
```
GET /pwork/list?tab=hot
  → AuthInterceptor：白名单命中，放行（不解析 token）
  → Service：tab=hot → Redis 命中? 是→返回缓存 : 查 view_work_hot → 回填缓存(60s)
  → 200 列表
```
> 触发登录的动作（点赞/收藏/关注/发布/我的）在**前端**先拦一次（跳登录页），后端 401 兜底。

**③ 发布 → 审核 → 可见**
```
POST /upload/work（token）
  → 校验大小 ≤10MB、类型 jpg/png
  → ExifStripper：读 EXIF(焦距/光圈/快门/ISO/镜头/机型) → 重写图（去 GPS/序列号）→ 存 uploads/work/
  → 写 work_exif(pid 由前端回传后写)  ← 注：先在 POST /pwork 里落 work_exif
  → 返回 {url, exif, exifStripped}

POST /pwork {title, desc, imageUrl, categoryId}
  → MsgSecCheck.text(title+desc) ──拒绝──> 422 content_rejected（不落库）
  → INSERT pwork(wstatus='待审核') + work_exif + work_embedding(status='pending')
  → 异步：投递建索引任务（见 ⑤）
  → 201 {pid, status:'待审核'}

后台 PUT /admin/work/{pid}/approve
  → 校验当前状态=待审核（否则 409）
  → UPDATE wstatus='展示' → 前台列表可见
```

**④ 点赞（幂等 + Java 事务维护计数）**
```
POST /like/{pid}   @Transactional
  → SELECT 1 FROM liketable WHERE uid=? AND targetid=? AND targettype='帖子'
      已存在 → 直接返回当前 count（幂等，不报错）
  → INSERT liketable(uid, targetid=pid, targettype='帖子')
  → UPDATE pwork SET likep = likep + 1 WHERE pid = ?      -- 计数由 Java 维护
  → SELECT likep FROM pwork WHERE pid=?  → 200 {liked:true, count}

DELETE /like/{pid}   @Transactional
  → DELETE ... （0 行也返回成功，幂等）
  → 命中才 UPDATE pwork SET likep = likep - 1 (且不 <0)
  → {liked:false, count}
```
> 卡 00 已删除计数触发器 —— **Java 与 DB 不再双写**；并发下 `likep=likep+1` 是原子更新，不需要额外锁。

**⑤ 检索（建索引 / 查询 / 降级）**
```
建索引（异步，status=pending）
  → ClipClient.encodeImage(url) → float32[512] → UPDATE work_embedding(status='ready')
  → 失败：status='failed', err_msg=…（后台可重试 /admin/search/reindex）

查询 GET /search?mode=semantic&q=海边日落
  → ClipClient.encodeText(q) → float[512]
  → SELECT pid, vec FROM work_embedding WHERE status='ready'  → 应用层余弦 → Top-K
  → join view_work_detail 取展示字段 → 200 {mode:'semantic', list}

降级：ClipClient 超时/异常 → 走 LIKE 关键词 → 200 {mode:'keyword', degraded:true}
      （**不返回 503**，用户看到"智能检索暂不可用"提示）
```

## §9 可测性约束（每模块）

**硬约束**：凡是断言"列表/详情/热门榜"的测试，**必须连真 MySQL**（H2 没有 `view_work_detail` 等 6 个视图，会静默退化成空表断言）；凡是限流测试，**必须连真 Redis**。计数已从触发器移到 Java，可单测（但仍需集成测验证并发）。

**代码风格约束（用户 2026-10-18 强调：必须与现有代码一致；其中类名与日志按规范）**：所有实现卡必须遵守 `docs/代码风格.md`，要点——
- **类名一律 PascalCase**（`UserController`）；存量 **9 个**小写 Controller 由**卡 11** 统一迁移
- 4 空格 + CRLF；`@Autowired` 字段注入；Service 接口 + Impl 三件套
- 公共方法 `/** @param @return */`；**非平凡语句带中文行尾注释**；分段用 `// ------------------- 标题 -------------------`
- 单表走 MyBatis-Plus，复杂查询走 Mapper XML + resultMap，分页走 PageHelper
- **日志统一 SLF4J**（`LoggerFactory` + `{}` 占位符），**禁 `System.out`**、禁打印手机号/密码/openid/token
- **禁**：整文件重排、引入 DTO/异常体系/Lombok builder、在业务卡里顺手重构旧代码
> 派工单必须附「风格自检：`git diff --numstat` 不得出现整文件重排」。
