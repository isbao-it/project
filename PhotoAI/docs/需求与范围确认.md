## 1. 背景与目标

**要解决的问题**：现有系统是"数据库设计完整、后端只写了一半"的摄影社区原型——评论/点赞/分类/订单四个模块的 Controller 是空类，AI 模块一行没有，测试为 0。

**项目目标**（可观察）：
1. 补齐社区主体闭环：发布 → 审核 → 浏览 → 评论/点赞 → 分类筛选；
2. 加入**一个**可量化的 AI 创新点：跨模态检索（以文搜图/以图搜图）+ 与关键词检索的对比数据；
3. 具备工程交付形态：一键启动（Docker Compose）、真实测试、部署说明；
4. 文档与系统一致（论文第 3/4/6 章要的 E-R、权限矩阵、测试数据都能从系统直接产出）。

**成功标准**：
- 论文第 6 章能用**真实跑出**的测试数据填满（不是编的）；
- 跨模态检索 Top-5 命中率 ≥ 70%（20 条标注查询）、P95 延迟有实测值；
- 换台电脑按 README 能在 10 分钟内跑起来。

## 3. 核心使用流程

**场景 1：用户发布作品**
小程序登录 → 选图 + 标题/描述/分类 → 提交 → 后端存图 + 剥离 GPS/序列号 → 文本过 `msgSecCheck` → 作品状态 = **待审核**（前台列表不可见）→ 管理员在后台**通过** → 前台可见、进入检索索引。

**异常流程**

| 情况        | 用户看到什么          | 系统行为                   |
| --------- | --------------- | ---------------------- |
| 文本审核不通过   | "内容不合规，请修改"     | 拒绝落库，记日志               |
| 图片超过 10MB | "图片过大"          | 前端压缩或拒绝                |
| AI 服务不可用  | 搜索框提示"智能检索暂不可用" | 自动退回关键词检索              |
| Redis 不可用 | 无感              | fail-open 放行 + WARN 日志 |

## 4. 数据与依赖

| 对象            | 说明                                  | 敏感                          |
| ------------- | ----------------------------------- | --------------------------- |
| MySQL `db_pg` | 9 表 + 6 视图 + 17 触发器（`photoai.sql`）  | 种子数据含 10 个真实手机号 → **推库前脱敏** |
| Redis         | 限流 + 热门榜缓存                          | 否                           |

| **游客** | 未登录可读：作品列表、作品详情、画廊、分类；其余 401 | 否 |
| 多模态模型（CLIP）   | 本地推理，模型权重不入 git                     | 否                           |

## 5. 非功能要求

- **可离线演示**：核心功能（浏览/发布/评论/点赞/限流）不依赖外网；AI 检索本地推理；断网时降级关键词。
- **性能**：热门榜接口 P95 ≤ 300ms（缓存后）；检索 Top-5 ≤ 1.5s（单图）。
- **安全**：越权 = 0（接口级角色校验）；不回显原文（日志不打印手机号/密码）；EXIF 不上传。
- **配置安全**：DB 口令、JWT 密钥**只从环境变量读**，`application.yml` 不留真实口令、不留可用默认密钥；种子数据手机号推库前脱敏。
- **交付形态**：源码 + `docker-compose.yml` + README + 演示视频。
